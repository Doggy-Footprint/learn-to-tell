# 캐시 TTL 정하기 (20261019-cache-ttl)
- 작업: 상품 정보 API에 캐시를 붙이며 TTL 길이(원본 부하 vs 오래된 응답)를 정한다.
- 진단: HTTP 요청·응답 알고 있음 / 캐시 hit·miss 애매함 / TTL과 만료 아예 모름 / 오래된 응답 비율·원본 부하 트레이드오프 아예 모름. 학습 수준은 "TTL과 만료"(진단은 실험 고정값).
- 이번 결정: 보류(실험이라 이해 확인을 하지 않음). 수업의 가정 수치에서는 원본 35/s·오래된 응답 5% 한도를 함께 맞추는 TTL이 60s~5m이었다.
- 선택을 바꾸는 조건: 상품별 요청 간격 분포(롱테일 비중), 필드별 변경 빈도, 원본 DB 한도, 오래된 가격 허용 시간, 필드를 따로 캐시할 수 있는지 여부.
- agent에게 할 질문: 접근 로그에서 상품별 요청 간격 분포를 뽑아 줄래? / 원본 DB 한도와 가격 표시 허용 지연은 누구에게 확인해야 해? / 상품 응답을 필드별로 나눠 캐시하려면 API를 어떻게 바꿔야 해?

## 주장 검토
- 틀림 — 7: 3·5와 모순. 레버 허용은 이중결과 원리의 비례성 조건에 기대므로, 레버에서 구하는 수를 1명으로 줄이면 의무론 판정도 바뀐다. 고친 문장: "행위 방식을 바꾸면 의무론 판정이 움직이고 공리주의 판정은 움직이지 않는다. 구하는 수를 바꾸면 공리주의 판정이 움직인다. 의무론 판정은 행위가 제약에 걸리지 않을 때만(비례성) 수에 반응하고, 제약에 걸리면 수가 아무리 커도 움직이지 않는다. 이 단순 모델에는 문턱이 없다." 모델·sweep·기대값(갈림 칸 수)이 이 문장과 맞는지도 다시 본다.

- BOM (b,d) → D, I: (4,2) 20,16; (4,4) 340,912; (3,5) 363,1278; (2,6) 126,516; (6,5) 9330,35460; (6,4) 1554,4356. I > 3D는 모든 b에서 정확히 d ≥ 5. C = Σ i·bⁱ는 실제 트리 조상 수와 일치(반사 트리플 제외).
- 추론 누적: (가) rdfs9+rdfs11 = 4 [DriveMotor subClassOf Part(스키마 수준), M-200 a ElectricalPart, M-200 a Part, B-18 a Part] — 데이터 추론만 세면 3. 어느 쪽으로 세는지 명시. (나) +rdfs2 = 5 (+C-21 a Part). (다) +prp-trp = 6 (+C-21 partOf D-300).
- 범위 표기: 전체 RDFS 함의는 rdfs4a/4b, rdf1도 비공리 트리플을 많이 만든다 → "이 네 규칙만" 명시. rdfs2·rdfs9·rdfs11은 RDFS, prp-trp는 OWL 2 RL 규칙임을 표기.
- SPARQL: `?part :partOf :D-300` → M-200, B-18 (추론 켜면 + C-21); `+ :suppliedBy ?s` → (M-200, hanbit), (B-18, daesung); `:partOf+ :D-300` → M-200, B-18, C-21; `?x a :ElectricalPart` → B-18 / 추론 켜면 B-18, M-200. `:partOf+`는 BGP가 아니라 property path라는 용어를 바로잡는다.
- SHACL: 대상 M-200, B-18, C-21. 위반 2건: C-21 MinCount, M-200 MaxCount. B-18 통과. SHACL은 기본적으로 RDFS/OWL 추론을 하지 않는다(클래스 대상의 subClassOf만 예외).
페이지 기대값과 대조해 다르면 고친다.

# 부품 데이터 모델: 테이블 vs 온톨로지·SHACL (20261019-ontology-triples)
