제품·부품 데이터 모델 결정을 위한 학습 챕터

테이블 스키마로 충분한가, 온톨로지와 SHACL을 얹어야 하는가

SQL과 JSON에 익숙한 백엔드 개발자를 위해 RDF, RDFS, OWL, SHACL을 기초부터 설명합니다. 읽는 시간은 60~90분 정도이고, 중간중간 직접 만져 보는 실습 6개와 마지막 서술 퀴즈 8문항이 있습니다.

0. 결론 먼저: 이 챕터가 답하려는 질문

질문은 "우리 제품·부품 데이터를 관계형 테이블로 표현할 것인가, 아니면 RDF 그래프 위에 온톨로지(RDFS·OWL)로 의미를 정의하고 SHACL로 검증할 것인가"입니다. 이 질문은 사실 세 개의 독립적인 질문이 섞여 있습니다.

  1. 저장·표현: 데이터를 행과 열로 둘 것인가, 주어–술어–목적어 트리플 그래프로 둘 것인가?
  2. 추론: 명시적으로 적지 않은 사실(예: "이 볼트는 체결 부품이다", "이 모듈은 차량의 일부다")을 규칙에서 자동으로 이끌어 내야 하는가?
  3. 검증: 들어오는 데이터가 기대하는 모양(필수 속성, 개수, 값 범위)을 갖췄는지 어떻게 강제할 것인가?

테이블은 1과 3을 한 덩어리로 해결합니다. 스키마가 곧 저장 형태이자 검증 규칙입니다. 반면 RDF 진영은 이 세 가지를 분리합니다. RDF는 저장, RDFS·OWL은 의미와 추론, SHACL은 검증을 맡습니다. 분리는 유연함을 주지만 그만큼 고를 것도, 운영할 것도 많아집니다.

미리 보는 판단 기준. 다음 중 둘 이상이 강하게 해당하면 온톨로지 계층을 진지하게 검토할 가치가 있습니다. (a) 분류 체계가 깊고 자주 바뀌며 여러 갈래로 겹친다. (b) 서로 다른 출처(ERP, PLM, 공급사 카탈로그, 표준 분류)의 데이터를 같은 의미로 묶어야 한다. (c) "A는 B의 일부"처럼 전이적 관계를 따라가는 질의가 핵심이다. (d) 데이터 모델 자체를 외부와 공유·교환해야 한다. 반대로 데이터가 한 시스템 안에서 생성되고, 구조가 안정적이며, 트랜잭션 무결성이 핵심이라면 테이블 스키마(필요하면 JSON 컬럼과 재귀 CTE)로 충분한 경우가 많습니다. 이 챕터의 나머지는 이 문장들을 스스로 판단할 수 있도록 근거를 쌓는 과정입니다.

1. 테이블 스키마가 실제로 보장하는 것

온톨로지를 이해하는 가장 빠른 길은, 익숙한 테이블이 무엇을 "당연하게" 해 주고 있는지 먼저 의식하는 것입니다. 다음 스키마를 예로 들겠습니다.

CREATE TABLE manufacturer (
  id   TEXT PRIMARY KEY,
  name TEXT NOT NULL
);
CREATE TABLE part (
  id              TEXT PRIMARY KEY CHECK (id ~ '^P-[0-9]{4}$'),
  name            TEXT NOT NULL,
  category        TEXT NOT NULL,          -- 'Bolt', 'Nut', 'Cable' ...
  weight_kg       NUMERIC CHECK (weight_kg >= 0),
  manufacturer_id TEXT NOT NULL REFERENCES manufacturer(id)
);
CREATE TABLE bom (                         -- Bill of Materials
  parent_id TEXT REFERENCES part(id),
  child_id  TEXT REFERENCES part(id),
  qty       INT  NOT NULL CHECK (qty > 0),
  PRIMARY KEY (parent_id, child_id)
);

이 스키마는 조용히 네 가지 가정을 하고 있습니다.

1.1 닫힌 세계 가정 (Closed World Assumption, CWA)

SELECT * FROM part WHERE manufacturer_id = 'M-ACME'에 어떤 부품이 안 나오면, 우리는 "그 부품은 ACME가 만들지 않았다"고 결론 내립니다. 데이터베이스에 없는 사실은 거짓이라고 보는 것, 이것이 닫힌 세계 가정입니다. 사내 시스템에서는 대부분 맞는 가정입니다. 우리가 데이터의 유일한 주인이기 때문입니다.

1.2 고유 이름 가정 (Unique Name Assumption, UNA)

기본키가 P-0001과 P-0002인 두 행은 서로 다른 부품입니다. 너무 당연해서 가정이라고 부르기도 어색하지만, 뒤에서 OWL이 이 가정을 하지 않는다는 점이 매우 중요해집니다.

1.3 스키마 우선 (schema-on-write)

컬럼에 없는 정보는 넣을 수 없습니다. 케이블에만 있는 "피복 재질"이나 볼트에만 있는 "나사 규격"을 추가하려면 컬럼을 추가하거나(대부분 NULL), 하위 테이블을 만들거나(조인 증가), JSON 컬럼에 넣거나(검증 약화), EAV(Entity–Attribute–Value) 테이블을 만들어야 합니다. 부품 종류가 수백 개로 늘어날 때 테이블 설계가 괴로워지는 지점이 바로 여기입니다.

1.4 의미는 코드와 사람 머릿속에

category = 'Bolt'인 행이 "체결 부품"이기도 하다는 사실은 스키마 어디에도 없습니다. 애플리케이션 코드의 if category in ('Bolt','Nut','Screw')나 위키 문서에 있습니다. 다른 팀이 이 데이터를 받아 가면 그 의미도 함께 복사해 가야 합니다.

정리: 테이블이 잘하는 것과 약한 것
잘하는 것약한 것
트랜잭션, 동시성, 참조 무결성

2. RDF: 모든 것을 트리플로

RDF(Resource Description Framework)는 모든 사실을 주어 – 술어 – 목적어 세 칸짜리 문장, 즉 트리플로 표현합니다. 트리플의 집합은 방향 있는 라벨 그래프가 됩니다. 노드는 주어와 목적어, 간선은 술어입니다.

2.1 IRI: 전역 식별자

주어와 술어는 IRI(웹 주소 꼴의 전역 식별자)입니다. https://data.example.com/part/P-0001처럼요. 매번 길게 쓰기 귀찮으니 접두어를 씁니다: ex:P-0001. 테이블의 기본키는 "이 테이블 안에서" 유일하지만, IRI는 "전 세계에서" 유일하도록 설계됩니다. 그래서 다른 회사 데이터와 그래프를 합쳐도 충돌하지 않고, 같은 IRI라면 자동으로 같은 노드로 합쳐집니다. 합치기가 그냥 트리플 집합의 합집합이라는 점이 RDF의 가장 큰 실용적 장점입니다.

목적어는 IRI일 수도 있고 리터럴(문자열, 숫자, 날짜 등 타입이 붙은 값)일 수도 있습니다.

2.2 Turtle 문법 한눈에 보기

@prefix ex:   <https://data.example.com/> .
@prefix rdf:  <http://www.w3.org/1999/02/22-rdf-syntax-ns#> .
@prefix xsd:  <http://www.w3.org/2001/XMLSchema#> .

ex:P-0001 rdf:type          ex:Bolt ;          # ';' 는 같은 주어 반복
          ex:name           "M8 육각볼트" ;
          ex:weightKg       "0.012"^^xsd:decimal ;
          ex:manufacturer   ex:M-ACME .

rdf:type(줄여서 a)은 "~의 인스턴스이다"를 뜻합니다. 테이블의 category 컬럼이 RDF에서는 클래스 소속 관계가 되는 셈입니다. 한 개체가 여러 클래스에 동시에 속할 수 있다는 점이 다릅니다.

실습 1 · 행을 트리플로

아래 행 값을 바꾸면 같은 정보가 트리플로 어떻게 표현되는지 바로 보입니다. "빈 값" 칸을 비워 보세요. 테이블에서는 NULL이 남지만, RDF에서는 트리플 자체가 사라집니다.

idnamecategoryweight_kgmanufacturer_id

2.3 NULL이 없다는 것의 의미

RDF에는 NULL이 없습니다. 값이 없으면 트리플을 쓰지 않습니다. 이 사소해 보이는 차이가 다음 절의 "열린 세계"와 연결됩니다. 트리플이 없다는 것은 "값이 없다"가 아니라 "이 그래프는 그것에 대해 아무 말도 하지 않는다"입니다.

2.4 RDF 자체는 아무것도 강제하지 않는다

RDF는 스키마가 없는 표현 형식입니다. 볼트에 무게가 두 개 있어도, 제조사가 문자열이어도, 오타 난 술어 ex:manufactuer를 써도 RDF는 아무 불평도 하지 않습니다. JSON과 비슷한 자유도입니다. 그래서 RDF만 도입하면 오히려 데이터 품질이 떨어집니다. 의미를 주는 RDFS·OWL과, 모양을 강제하는 SHACL이 필요한 이유입니다.

3. RDFS: 가장 가벼운 추론

RDFS(RDF Schema)는 클래스와 속성에 대한 어휘를 몇 개 추가합니다. 핵심은 네 개입니다.

어휘뜻추론 규칙
rdfs:subClassOf클래스 A는 B의 하위 클래스x가 A이면 x는 B이다. 또 A⊂B, B⊂C이면 A⊂C
rdfs:subPropertyOf속성 p는 q의 하위 속성x p y 이면 x q y
rdfs:domain속성 p의 주어 쪽 클래스x p y 이면 x는 domain 클래스이다
rdfs:range속성 p의 목적어 쪽 클래스x p y 이면 y는 range 클래스이다
가장 흔한 함정. 백엔드 개발자는 rdfs:domain을 "이 속성은 Part에만 쓸 수 있다"는 제약으로 읽기 쉽습니다. 그렇지 않습니다. RDFS의 domain은 추론 규칙입니다. Part가 아닌 무언가에 ex:manufacturer를 붙이면 에러가 나는 대신 "그렇다면 그것도 Part이다"라는 새 사실이 생깁니다. 오타나 잘못된 데이터가 조용히 분류를 오염시킬 수 있다는 뜻입니다. 아래 실습에서 직접 확인해 보세요.
실습 2 · RDFS/OWL 추론 시뮬레이터

왼쪽은 스키마(온톨로지) 트리플, 오른쪽은 인스턴스 데이터입니다. 적용할 규칙을 고르고 "추론 실행"을 누르면, 명시된 트리플(회색)과 추론된 트리플(보라색, 어떤 규칙에서 나왔는지 표시)이 나타납니다. 텍스트를 직접 고쳐도 됩니다. 한 줄에 트리플 하나, 공백으로 구분합니다.

온톨로지(TBox)
데이터(ABox)

생각해 볼 것: ex:Cable-7은 타입이 적혀 있지 않은데 무엇으로 분류되었나요? 이것은 의도한 결과일까요, 데이터 오류가 조용히 묻힌 것일까요? 그리고 OWL 규칙 두 개를 켜면 CAR-A가 가진 부품은 몇 개로 늘어나나요?

3.1 추론은 "질의 시점의 뷰"로 이해하면 쉽다

추론 결과를 실제로 저장하는 방식(materialization, 정방향 추론)과, 질의할 때 규칙을 적용하는 방식(역방향 추론, 질의 재작성)이 있습니다. SQL에 비유하면 전자는 머티리얼라이즈드 뷰, 후자는 일반 뷰입니다. 전자는 질의가 빠르지만 원본이 바뀔 때 갱신 비용이 들고, 후자는 저장은 가볍지만 질의가 느려질 수 있습니다.

그렇다면 SQL에서도 같은 일을 할 수 있지 않을까요? 맞습니다. category 계층 테이블과 재귀 CTE로 "모든 Fastener 조회"를 구현할 수 있습니다. 차이는 규칙이 어디에 있느냐입니다. SQL에서는 규칙이 각 질의와 애플리케이션 코드에 흩어져 있고, RDFS에서는 규칙이 데이터와 같은 형식의 트리플로 함께 배포됩니다. 데이터를 받아 가는 쪽이 같은 추론기를 돌리면 같은 결론에 도달합니다.

-- SQL로 흉내 낸 subClassOf 추론
WITH RECURSIVE sup(cls, ancestor) AS (
  SELECT child, parent FROM class_hierarchy
  UNION
  SELECT s.cls, h.parent FROM sup s JOIN class_hierarchy h ON h.child = s.ancestor
)
SELECT p.* FROM part p
WHERE p.category = 'Fastener'
   OR p.category IN (SELECT cls FROM sup WHERE ancestor = 'Fastener');

4. OWL: 더 강한 의미와 열린 세계

OWL(Web Ontology Language)은 RDFS 위에 훨씬 풍부한 어휘를 얹은 언어입니다. 형식적으로는 서술 논리(Description Logic)에 기반하고, 추론기는 "주어진 공리들로부터 논리적으로 반드시 따라오는 것"을 모두 계산합니다.

4.1 자주 쓰는 OWL 구성

구성예추론 효과
owl:TransitivePropertypartOf볼트 ⊂ 브레이크 ⊂ 바퀴 ⊂ 차 ⇒ 볼트 partOf 차
owl:inverseOfhasPart ↔ partOf한쪽만 적어도 반대 방향이 생김
owl:equivalentClassERP의 erp:Screw ≡ PLM의 plm:Schraube두 시스템의 분류를 하나로 취급
owl:sameAs공급사 카탈로그의 부품 = 사내 부품두 IRI의 모든 사실을 공유
owl:disjointWithBolt와 Cable은 겹칠 수 없음둘 다인 개체가 생기면 불일치(inconsistency)
정의된 클래스(restriction)"Steel 재질 부품을 하나 이상 포함하는 조립품" = SteelAssembly조건을 만족하는 개체를 자동 분류
owl:FunctionalProperty / 최대 카디널리티부품의 제조사는 최대 1아래 4.3 참고. 에러가 아니라 sameAs 추론이 일어날 수 있음

마지막 줄의 "정의된 클래스"가 OWL을 RDFS와 구별하는 핵심 기능입니다. 사람이 일일이 분류하지 않아도, 조건을 기술하면 추론기가 해당 개체를 찾아 분류합니다. 규제 대상 부품 판정, 호환 부품 분류처럼 "조건으로 정의되는 범주"가 많고 그 조건이 자주 바뀌는 도메인에서 위력을 발휘합니다.

4.2 열린 세계 가정 (Open World Assumption, OWA)

OWL은 닫힌 세계를 가정하지 않습니다. 그래프에 "P-0001의 제조사"가 없다면, OWL은 "제조사가 없다"고 결론 내리지 않고 "아직 모른다"고 봅니다. 웹처럼 누구도 전체 정보를 갖지 않은 환경을 위해 설계되었기 때문입니다.

이 차이 때문에, owl:minCardinality 1("부품은 제조사를 최소 1개 가진다")을 선언해도 제조사가 비어 있는 부품이 에러가 되지 않습니다. 추론기는 "어딘가에 알려지지 않은 제조사가 존재한다"고 받아들입니다. SQL의 NOT NULL과는 정반대의 반응입니다.

4.3 고유 이름 가정이 없다

OWL에서 두 IRI는 다르다고 명시하지 않는 한 같은 대상을 가리킬 수도 있습니다. 그래서 "제조사는 최대 1개"라고 선언한 부품에 제조사 IRI가 두 개 달려 있으면, OWL 추론기는 오류를 내는 대신 "그 두 제조사는 같은 회사다(sameAs)"라고 추론합니다. 두 회사가 서로 다르다고 명시(owl:differentFrom)해 두었을 때에야 비로소 불일치가 됩니다.

실습 3 · 같은 데이터, 세 가지 반응

규칙 "부품의 제조사는 정확히 1개"를 SQL, OWL, SHACL 세 세계에서 각각 표현했다고 합시다. 데이터 상황을 고르면 각 세계가 어떻게 반응하는지 보여 줍니다.

4.4 OWL 프로파일과 계산 비용

OWL 2 전체(OWL 2 DL)의 추론은 계산 복잡도가 매우 높습니다. 그래서 실무에서는 표현력을 일부 포기하고 성능을 보장하는 프로파일을 고릅니다.

  • OWL 2 RL: 규칙 엔진(정방향 추론)으로 구현 가능. 대용량 데이터의 materialization에 적합. 트리플스토어 대부분이 지원.
  • OWL 2 EL: 거대한 클래스 계층(의료 용어 체계 등) 분류에 최적화. 다항 시간.
  • OWL 2 QL: 질의를 SQL로 재작성할 수 있게 설계. 기존 관계형 DB 위에 온톨로지를 "가상으로" 얹는 OBDA(Ontology-Based Data Access)에 쓰임.

마지막 항목은 이 챕터의 질문과 직결됩니다. "테이블이냐 온톨로지냐"는 양자택일이 아닐 수 있습니다. 데이터는 그대로 관계형 DB에 두고, 그 위에 매핑과 온톨로지를 얹어 의미 질의만 그래프 방식으로 하는 구성도 가능합니다.

5. SHACL: 데이터 모양 검증

OWL이 "세계에 대해 참인 것"을 기술한다면, SHACL(Shapes Constraint Language)은 "이 데이터 그래프가 갖춰야 할 모양"을 기술합니다. SHACL은 닫힌 세계처럼 동작합니다. 그래프에 없는 것은 없는 것이고, sh:minCount 1을 어기면 위반 보고서가 나옵니다. 백엔드 개발자에게는 JSON Schema나 SQL 제약과 가장 비슷한 감각입니다.

ex:PartShape a sh:NodeShape ;
    sh:targetClass ex:Part ;                 # 검증 대상: Part의 모든 인스턴스
    sh:property [
        sh:path ex:manufacturer ;
        sh:minCount 1 ; sh:maxCount 1 ;
        sh:class ex:Company ;
    ] ;
    sh:property [
        sh:path ex:weightKg ;
        sh:datatype xsd:decimal ;
        sh:minInclusive 0 ;
    ] ;
    sh:property [
        sh:path ex:partNumber ;
        sh:pattern "^P-[0-9]{4}$" ;
    ] .

구성 요소는 세 가지입니다.

  • 타깃: 어떤 노드를 검사할지 (sh:targetClass, sh:targetNode, sh:targetSubjectsOf 등)
  • 경로: 그 노드에서 어떤 속성을 따라갈지 (sh:path, 시퀀스·역방향·반복 경로도 가능)
  • 제약: 개수, 타입, 값 범위, 패턴, 다른 shape 준수 여부, 필요하면 SPARQL로 작성한 임의 조건

SHACL 검증기는 결과를 sh:ValidationReport라는 RDF 그래프로 돌려줍니다. 어떤 노드의 어떤 경로가 어떤 제약을 어겼는지 기계가 읽을 수 있는 형태입니다. 데이터 수집 파이프라인에서 "불량 레코드 격리"에 그대로 쓸 수 있습니다.

실습 4 · SHACL 검증 플레이그라운드

데이터를 고치고 "검증"을 누르세요. 위 ex:PartShape가 적용됩니다. 제약을 껐다 켜며 어떤 위반이 사라지는지 보세요. "검증 전에 RDFS 추론 실행"을 켜면 결과가 어떻게 달라지는지도 확인하세요.

관찰 포인트: 추론을 끈 상태에서는 rdf:type ex:Bolt로만 적힌 P-0001과 P-0003이 sh:targetClass ex:Part의 대상이 되나요? 실제 SHACL 표준은 rdfs:subClassOf 트리플이 데이터 그래프 안에 있으면 하위 클래스 인스턴스도 타깃에 포함하지만, 그 트리플이 별도의 온톨로지 파일에만 있으면 포함하지 않습니다. 이 시뮬레이터는 클래스 계층이 데이터 그래프에 없다고 가정합니다.

5.1 SHACL과 OWL은 경쟁 관계가 아니다

6. 추론과 검증을 함께 쓰는 법

실무 파이프라인은 대개 다음 순서를 따릅니다.

추론을 검증보다 먼저 두는 이유는 실습 4에서 본 것처럼 추론이 검증 대상과 값을 바꾸기 때문입니다. 반대로 추론이 잘못된 데이터를 "그럴듯하게" 만들 수도 있습니다(실습 2의 Cable-7). 그래서 원본 데이터에 대한 1차 SHACL 검증(오타 술어, 타입 누락 탐지)을 추론 전에 한 번 더 두는 팀도 많습니다.

6.1 설계 원칙 몇 가지

  • domain/range는 아껴 쓴다. 검증 의도라면 SHACL로 표현하고, domain/range는 정말로 분류를 이끌어 내고 싶을 때만 선언합니다.
  • owl:sameAs는 전염된다. 하나의 잘못된 sameAs가 두 개체의 모든 속성을 섞어 버립니다. 개체 통합은 신뢰도 높은 키가 있을 때만, 가능하면 별도 그래프에 두어 되돌릴 수 있게 합니다.
  • 프로파일을 먼저 정한다. "OWL을 쓴다"가 아니라 "OWL 2 RL 범위만 쓴다"처럼 정해야 성능과 도구 선택이 결정됩니다.
  • 온톨로지도 코드처럼 버전 관리한다. 클래스 계층 변경은 스키마 마이그레이션과 같은 무게의 변경입니다.

7. 결정 변수와 판단 도우미

이제 원래 질문으로 돌아갑니다. 판단을 가르는 변수는 기술 자체보다 데이터와 조직의 성질에 있습니다.

결정 변수테이블 쪽으로 기우는 경우온톨로지+SHACL 쪽으로 기우는 경우
분류 체계얕고 안정적(카테고리 10여 개)깊고 다중 상속, 자주 변경, 표준 분류(ECLASS, UNSPSC 등)와 연결
속성 이질성부품 종류 간 속성이 대체로 같음종류마다 속성 집합이 크게 다르고 계속 늘어남

중간 선택지도 기억해 두세요.

  • 관계형 + JSON 컬럼 + JSON Schema: 속성 이질성만 문제라면 대개 이것으로 충분합니다.
  • 관계형 + 분류 계층 테이블 + 재귀 CTE: 얕은 추론(상속)만 필요할 때.
  • 관계형 원천 + 가상 온톨로지 계층(OBDA, R2RML 매핑): 트랜잭션은 DB에, 통합 의미 질의는 그래프로.
  • RDF + SHACL만 (OWL 없이): 유연한 스키마와 통합은 원하지만 추론은 불필요할 때. 생각보다 흔하고 운영이 단순합니다.
  • 속성 그래프 DB: 관계 탐색은 필요하지만 표준 의미·추론·외부 교환은 필요 없을 때.

8. 자주 하는 오해

"온톨로지를 쓰면 데이터 검증이 된다"

OWL은 열린 세계라서 누락을 잡지 못하고, 카디널리티 위반은 sameAs 추론으로 흡수되기도 합니다. OWL이 잡는 것은 논리적 모순(disjoint 위반 등)뿐입니다. 데이터 품질 검증은 SHACL의 일입니다.

"rdfs:domain은 외래키 같은 제약이다"

제약이 아니라 추론 규칙입니다. 위반 대신 새 타입이 생깁니다.

"RDF로 바꾸면 스키마 변경이 공짜다"

저장 형태 변경은 공짜에 가깝지만, 온톨로지·SHACL shape·SPARQL 질의·매핑을 함께 바꿔야 합니다. 비용이 사라지는 것이 아니라 다른 곳으로 옮겨집니다.

"테이블이냐 온톨로지냐 하나만 골라야 한다"

OBDA나 "원천은 관계형, 통합 계층만 그래프"처럼 섞는 구성이 흔합니다. 질문을 "어느 계층에서 어떤 문제를 풀 것인가"로 바꾸면 선택지가 넓어집니다.

"추론을 많이 할수록 좋다"

추론은 질의 성능, 디버깅 난이도, 오류 전파 범위를 함께 키웁니다. 필요한 규칙만 켜고 프로파일을 제한하는 편이 운영에 유리합니다.
