1. 캐시가 하는 일: hit, miss, TTL, stale

캐시는 원본(DB, 상품 서비스)에서 가져온 응답을 잠시 복사해 두고, 같은 요청이 오면 원본에 가지 않고 복사본을 돌려주는 장치다. Redis, 애플리케이션 메모리, CDN, 브라우저가 모두 캐시가 될 수 있다.

용어뜻상품 API 예시
hit캐시에 유효한 복사본이 있어 그걸로 응답GET /products/123을 Redis 값으로 응답
miss복사본이 없거나 만료돼 원본까지 다녀옴DB에서 상품 조회 → Redis에 저장 → 응답
hit ratio전체 요청 중 hit 비율95%면 원본은 요청의 5%만 받는다
TTL (time to live)복사본을 저장한 뒤 유효하다고 볼 시간SET product:123 ... EX 60 → 60초 뒤 만료
stale복사본이 원본의 현재 값과 다른 상태가격이 9,900원 → 8,900원으로 바뀌었는데 캐시는 아직 9,900원
핵심 관찰. TTL 기반 캐시는 "원본이 바뀌었는지"를 모른다. 단지 "저장한 지 T초가 지났는지"만 본다. 그래서 TTL 동안 원본이 바뀌면, 남은 시간 동안 stale 응답이 나간다. 최악의 경우 사용자는 최대 TTL만큼 오래된 정보를 본다.

2. TTL 하나가 두 숫자를 동시에 움직인다

TTL을 짧게 (예: 5초)TTL을 길게 (예: 1시간)
hit ratio낮음 → 원본 부하 큼높음 → 원본 부하 작음
stale최대 5초 늦음, stale 비율 낮음최대 1시간 늦음, stale 비율 높음
장애 시원본이 죽으면 캐시도 금방 비어 같이 죽음원본이 잠깐 죽어도 캐시가 버팀

즉 TTL은 "원본 부하"와 "신선도" 사이의 손잡이다. 정답은 서비스마다 다르고, 판단 근거는 아래 네 가지 숫자다.

  1. 요청 빈도 (키 하나당 초당 몇 번 읽히나): 자주 읽히는 키일수록 짧은 TTL로도 hit ratio가 높다.
  2. 변경 빈도 (상품 정보가 얼마나 자주 바뀌나): 거의 안 바뀌면 TTL을 길게 해도 stale이 드물다.
  3. stale 허용치 (늦은 정보가 얼마나 비싼가): 상품 설명이 1시간 늦는 것과 가격·재고가 1시간 늦는 것은 비용이 다르다.
  4. 원본 여유 (원본이 초당 몇 건을 견디나): 캐시가 없어도 버틸 수 있다면 TTL은 짧게 둬도 된다.

3. 계산해 보기: 간단한 수식

한 상품 키를 생각하자. 요청이 초당 평균 λ번 무작위로 오고, TTL이 T초라고 하자.

  • miss가 한 번 나면 그 순간부터 T초 동안은 모두 hit이다. 그동안 평균 λT번의 요청이 온다.
  • 따라서 "miss 1번 + hit λT번"이 반복된다.

hit ratio ≈ λT / (1 + λT)

원본 요청률(키 하나) ≈ λ / (1 + λT)  → λ가 크면 대략 1/T (TTL마다 1번)

예: 상품 하나가 초당 2번 읽히고 TTL 60초 → λT=120 → hit ratio ≈ 99.2%. 원본은 그 상품 때문에 60초에 1번만 조회된다.
반면 하루 3번 읽히는 비인기 상품(λ≈0.000035)은 TTL 60초여도 λT≈0.002 → hit ratio ≈ 0.2%. 거의 항상 miss다.

교훈 1. 상품 API 트래픽은 보통 소수 인기 상품에 몰린다(롱테일). 인기 상품은 짧은 TTL로도 충분히 hit이 나고, 비인기 상품은 TTL을 늘려도 hit ratio 개선이 작다. 그래서 "전체 hit ratio"는 TTL보다 트래픽 분포에 더 크게 좌우될 때가 많다.

상품 정보가 평균 μ번/초로 바뀐다고 하자(예: 하루 1번 → μ = 1/86400). hit 응답이 나갈 때 복사본의 나이는 0~T 사이에 고르게 퍼져 있으므로:

hit 응답이 stale일 확률 ≈ 1 − (1 − e−μT) / (μT)  ≈ μT / 2 (μT가 작을 때)

stale 응답의 평균 지연은 대략 T/2 이하, 최대 T

예: 하루 1번 바뀌는 상품, TTL 60초 → μT ≈ 0.0007 → 응답의 약 0.035%가 stale. TTL 1시간 → 약 2%.

교훈 2. stale 비율은 "TTL ÷ 변경 주기"에 비례하고, stale 최대 지연은 TTL 그 자체다. 사업적으로 중요한 건 대개 최대 지연("가격 변경이 최대 몇 초 후 반영되나")이다.

4. 시뮬레이터: 내 서비스 숫자를 넣어 보기

상품 N개, 전체 초당 요청 수, 인기 쏠림(Zipf 지수), 상품 변경 주기를 넣으면 TTL별로 hit ratio, 원본 QPS, stale 비율을 계산한다. 위 수식을 상품마다 적용해 합산한 결과다.

hit ratio
원본 요청 (req/s)
stale 응답 비율
최대 지연 (=TTL)

원본 요청 (req/s, 왼쪽 축, 로그) stale 응답 비율 (오른쪽 축, 로그) 원본 한계
이 모델이 무시하는 것
  • 요청이 무작위(Poisson)로 온다고 가정한다. 실제는 시간대별 파동이 있다.
  • 캐시 메모리가 충분해 만료 전 쫓겨나는(eviction) 일이 없다고 가정한다.
  • 동시 miss(stampede)는 반영하지 않는다. 인기 키가 만료되는 순간 원본 요청이 순간적으로 몰릴 수 있다(6절).
  • 모든 상품의 변경 주기가 같다고 가정한다.

만져 보며 확인할 것

  1. TTL을 1초 → 10초로 올릴 때와 10분 → 1시간으로 올릴 때, 원본 요청이 줄어드는 폭을 비교해 보라. (앞쪽이 훨씬 크다: 수확 체감)
  2. Zipf s를 0(균등)으로 내리면 hit ratio가 어떻게 되나? 1.2로 올리면?
  3. 변경 주기를 "1분"으로 바꾸면(실시간 재고 같은 데이터), 어떤 TTL에서도 stale 비율이 커진다. 이때는 TTL이 아니라 다른 도구가 필요하다.

5. 타임라인으로 보는 한 상품 키

한 키에 요청이 오고, 중간에 원본 값이 바뀌는 모습을 무작위로 생성한다. 초록=hit(신선), 빨강=hit(stale), 주황=miss.

관찰 포인트: 원본 값이 바뀐 직후(세로 점선)부터 다음 miss까지의 hit이 모두 빨강이다. TTL을 줄이면 빨간 구간이 짧아지는 대신 주황(원본 요청)이 늘어난다.

6. TTL만으로 부족할 때 쓰는 도구

도구무엇을 해결하나상품 API에서의 쓰임
쓰기 시 무효화 (invalidate on write)원본 변경 시 캐시 키를 지우거나 갱신 → stale을 TTL과 무관하게 줄임관리자가 가격 수정 → DEL product:123. 이렇게 하면 TTL을 길게 둬도 된다. TTL은 "무효화가 누락됐을 때의 안전망"이 된다.
stale-while-revalidate만료 직후엔 옛 값을 바로 주고 백그라운드에서 갱신 → 지연 없이 신선도 유지HTTP Cache-Control: max-age=60, stale-while-revalidate=30, 또는 앱 캐시에서 soft/hard TTL 구분
stale-if-error원본 장애 시 만료된 값이라도 응답상품 서비스 장애 때 페이지가 비지 않게
요청 병합 / 락 (single-flight)인기 키 만료 순간 수백 요청이 동시에 원본으로 가는 cache stampede 방지같은 키 miss는 1개만 원본 조회, 나머지는 결과 대기
TTL jitter배포·워밍 때 한꺼번에 저장된 키들이 동시에 만료되는 현상 분산TTL = 300초 ± 10% 무작위
필드별 분리신선도 요구가 다른 데이터를 다른 TTL로설명·이미지(긴 TTL) vs 가격·재고(짧은 TTL 또는 캐시 안 함)
negative caching없는 상품 ID 반복 조회로 원본 부하404도 짧게(예: 30초) 캐시
주의: 재고·결제 금액. 주문 시점의 최종 가격과 재고 확인은 캐시된 상품 API 값에 기대지 말고 원본에서 다시 확인하는 것이 일반적이다. 그러면 상품 조회 API의 TTL은 "화면에 잠깐 옛 값이 보이는 것"만 감수하면 되어 훨씬 길게 잡을 수 있다.

7. TTL 결정 절차 (체크리스트)

  1. 데이터를 신선도 요구별로 나눈다. 상품 응답의 필드 중 "늦게 보이면 돈/신뢰 문제가 되는 것"(가격, 재고, 판매 상태)과 아닌 것(이름, 설명, 이미지, 카테고리)을 구분한다.
  2. 각 그룹의 최대 허용 지연을 기획/운영과 숫자로 합의한다. 예: "가격 변경은 1분 안에 반영", "설명은 10분 안에". 이 숫자가 TTL의 상한이다(무효화를 안 쓴다면).
  3. 원본 한계를 잰다. 상품 서비스/DB가 초당 몇 건을 안전하게 처리하나. 4절 시뮬레이터에서 원본 요청이 이 값의 절반 이하가 되는 TTL이 TTL의 하한이다.
  4. 하한 ≤ 상한이면 그 사이에서 고른다. 보통 상한 쪽(신선도 허용 범위 안에서 가장 긴 값)에 jitter를 섞는다.
  5. 하한 > 상한이면 TTL만으로는 안 된다. 쓰기 시 무효화를 붙이거나, 필드를 분리하거나, 원본을 증설한다.
  6. 인기 키 stampede 대책(single-flight 또는 stale-while-revalidate)을 넣는다.
  7. 배포 후 측정하고 조정한다. hit ratio, 원본 QPS, 캐시 키 나이 분포, (가능하면) 원본과 캐시 값 불일치 샘플링을 대시보드에 둔다.
예시 결론 (가정이 다르면 숫자도 다르다)

상품 10만 개, 전체 500 req/s, 인기 쏠림 s≈1, 상품 정보는 하루 1번 정도 바뀜, 원본은 200 req/s까지 안전.
→ 설명·이미지: TTL 10분 + 쓰기 시 무효화.
→ 가격·판매 상태: TTL 30~60초 (허용 지연 1분), 주문 시 원본 재확인.
→ 인기 상품 stampede 대비 single-flight, TTL에 ±10% jitter.
