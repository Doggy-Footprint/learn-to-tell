# Raft 합의 — 리더 선출과 로그 복제 (overview)

대상: 분산 시스템 입문 개발자 / 매체: 아키텍처 화이트보드 / 결정: 합의 기반 저장소 선택

## 독자가 말할 수 있어야 하는 한 문장
"Raft는 과반수(quorum)가 투표한 리더 한 명만 로그를 쓰게 하고, 과반수에 복제된 항목만 커밋하므로, 노드가 죽어도 커밋된 데이터는 사라지지 않는다."

## 인과 사슬
1. 팔로워가 election timeout 동안 리더의 heartbeat를 못 받는다 → 후보(candidate)가 되어 term을 +1 하고 투표를 요청한다.
2. 과반수 표를 얻는다 → 그 term의 리더가 된다 (term당 투표는 노드마다 1회이므로 리더는 최대 1명).
3. 클라이언트 쓰기가 리더에 도착한다 → 리더가 자기 로그에 항목을 append한다 (아직 미커밋).
4. 리더가 AppendEntries로 팔로워에 복제한다 → 과반수(리더 포함)가 저장하면 리더가 commitIndex를 올린다.
5. 커밋된 항목만 상태 머신에 적용하고 클라이언트에 응답한다. 다음 heartbeat로 팔로워도 commitIndex를 따라간다.
6. 리더가 죽으면 1로 돌아가고, 최신 로그를 가진 후보만 과반수 표를 받을 수 있어 커밋 항목은 보존된다.

## 화면에 꼭 보일 것
- 노드 5개(리더 1, 팔로워 4), 각 노드의 로그 칸(index, term)과 term 번호.
- 관계: 투표 요청/응답, AppendEntries(복제), 커밋 경계(commitIndex).
- 강조점 하나: "과반수 = 5개 중 3개"가 되는 순간 항목이 커밋으로 바뀐다.

## 생성 순서 (틀리기 쉬움)
- 리더는 항목을 먼저 자기 로그에 쓰고, 그다음 복제한다. 커밋은 복제 응답이 과반수 모인 뒤에 생긴다.
- term은 후보가 되는 순간 올라가고, 리더 선출 결과보다 먼저 바뀐다.
- 팔로워의 commitIndex는 리더보다 한 박자 늦게(다음 AppendEntries에서) 올라간다.
- 리더 응답(클라이언트 ack)은 커밋 이후이지 append 이후가 아니다.

## 사실 점검표
- 과반수 = floor(N/2)+1. N=5 → 3, N=3 → 2, N=4 → 3(4개는 5개보다 장애 허용이 늘지 않음). 허용 장애 = N − 과반수: 5노드는 2대.
- 손 계산: 5노드에서 리더+팔로워 2 = 3개 저장 → 커밋. 리더+팔로워 1 = 2개 → 미커밋.
- 투표 요청은 term +1, 노드는 term당 한 표. 더 높은 term을 보면 리더도 즉시 팔로워로 내려간다.
- election timeout은 노드마다 무작위(예: 150–300ms)로 달라 동시 출마(split vote)를 줄인다. heartbeat 주기는 이보다 훨씬 짧다(예: 50ms).
- 후보의 로그가 상대보다 덜 최신이면(마지막 term, 그다음 index 비교) 표를 받지 못한다.
- 리더 로그가 다른 노드에 덮어쓰기될 수는 있어도, 커밋된 항목은 지워지지 않는다.

## 흔한 오해와 깨는 순간
오해: "리더가 로그에 썼으면 그 데이터는 안전하다(커밋이다)."
깨는 순간: 리더가 항목을 append한 직후 팔로워에 닿기 전에 죽는다. 새 리더가 뽑히고 그 항목은 사라진다. 클라이언트는 ack를 받지 못했으므로 모순이 없다. 반대로 3개에 복제된 항목은 리더가 죽어도 새 리더에게 남는다.

## 비트
1. 리더의 heartbeat가 끊기면 팔로워 하나의 타이머가 먼저 만료된다.
2. 후보가 term을 올리고 투표를 모아 과반수 3표로 리더가 된다.
3. 쓰기가 리더 로그에 들어가지만 아직 미커밋 상태다.
4. 복제 응답이 쌓여 3번째 저장이 확인되는 순간 커밋 경계가 넘어간다.
5. 리더가 죽어도 커밋 항목을 가진 노드만 새 리더가 될 수 있다.
6. 저장소 선택: 쓰기마다 과반수 왕복 지연을 치르는 대신 2대 장애까지 데이터 손실이 없다.
