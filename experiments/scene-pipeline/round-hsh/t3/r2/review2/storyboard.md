# Raft 합의 스토리보드 (overview)

## 독자가 말할 한 문장
"Raft는 과반수의 표로 리더 한 명을 뽑고, 리더만 로그를 쓰며, 과반수 서버에 복제된 항목만 커밋하므로, 서버 일부가 죽어도 모두가 같은 순서의 같은 기록을 갖는다."

## 인과 사슬
1. 팔로워가 election timeout(무작위, 예: 150~300ms) 동안 리더의 heartbeat를 못 받는다.
2. 그 팔로워가 term을 +1 하고 후보가 되어 자기에게 투표한 뒤 RequestVote를 보낸다.
3. 각 서버는 term마다 한 표만 준다. 후보 로그가 자기 것보다 최신 이상이어야 준다.
4. 과반수 표를 얻으면 리더가 되고 곧바로 heartbeat(빈 AppendEntries)를 보내 다른 후보를 눌러 앉힌다.
5. 클라이언트 요청은 리더만 받는다. 리더가 자기 로그 끝에 항목을 먼저 추가한다(아직 미커밋).
6. 리더가 AppendEntries로 팔로워에 복제한다. 과반수(리더 포함)가 저장했다는 응답이 오면 커밋한다.
7. 리더가 commitIndex를 다음 AppendEntries에 실어 보내면 팔로워도 커밋하고 상태 기계에 적용한다.

## 화면에 꼭 보일 것
- 서버 5대(S1~S5), 각자의 term, 역할(팔로워/후보/리더), 로그 칸(index, term).
- 투표 화살표(후보→서버), 복제 화살표(리더→팔로워), 과반수 표시(5대 중 3).
- 강조점 하나: "과반수"가 선출과 커밋 두 곳에서 같은 역할을 한다.

## 생성 순서 (틀리기 쉬움)
- term 증가와 자기 투표가 먼저, 그다음에 RequestVote 전송. 리더는 표를 센 뒤에야 생긴다.
- 로그 항목은 리더 로그에 먼저 생기고(미커밋), 팔로워 복제 후, 과반수 확인 뒤에 커밋 표시가 붙는다. 커밋은 "복제 후"이지 "복제 전"이 아니다.
- 팔로워의 커밋은 리더보다 한 박자 늦다(commitIndex를 다음 메시지로 전달받음).

## 사실 점검표
- 과반수 = floor(N/2)+1. N=5면 3, N=4도 3, N=3이면 2. 5대는 2대 장애까지 견딘다(5-2=3 ≥ 3). 3대 죽으면 선출도 커밋도 불가.
- 짝수 대수는 이득이 없다: 4대도 1대 장애만 견딘다(4-2=2 < 3).
- 예: S1 리더, term 3. 항목 index 7을 S1,S2,S3에 저장하면 3/5 → 커밋. S4,S5는 아직 없어도 된다.
- 한 term에 리더는 최대 한 명. 서버는 term당 투표 한 번.
- 더 높은 term을 보면 리더도 즉시 팔로워로 내려간다.
- 커밋된 항목은 사라지지 않는다(새 리더는 최신 로그를 가진 서버 중에서만 나옴).
- 무작위 timeout은 동시 출마로 인한 표 분산(split vote)을 줄이려는 것이다.

## 흔한 오해
"리더가 항목을 자기 로그에 쓰면 그 순간 커밋이다" 또는 "모든 서버가 받아야 커밋이다."
깨는 순간: 리더가 index 7을 쓴 직후는 미커밋(회색). S2, S3 응답으로 3/5가 되는 순간 커밋되고, S4가 죽어 있어도 그대로 커밋 상태다.

## 비트
1. 리더가 사라지면 팔로워 하나의 timer가 먼저 끝나 후보가 된다(term +1).
2. 표는 term당 한 장씩, 과반수(3/5)를 모은 쪽만 리더가 된다.
3. 리더가 heartbeat를 보내자 나머지는 다시 조용한 팔로워가 된다.
4. 클라이언트 요청은 리더 로그에 미커밋으로 먼저 생긴다.
5. 복제 응답이 3/5에 닿는 순간 커밋되고, 느리거나 죽은 서버가 있어도 진행된다.
6. 저장소 선택 관점: 과반수를 못 모으면 멈춘다. 일관성을 위해 가용성을 양보하는 구조다.
