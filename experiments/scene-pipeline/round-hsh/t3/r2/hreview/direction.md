# Raft 합의 장면 방향

## 초안별 진단

**a.html**: 5대를 커스텀 SVG 상자로 그리고, 상자마다 역할·term·로그 칸(index 4~7)을 넣었다. 가운데 과반 패널과 패킷이 함께 움직인다. 비트 순서(timer → 후보 → 표 → 리더 → heartbeat → 미커밋 기록 → 복제 → 응답 → 커밋 → 팔로워 커밋)는 스토리보드 생성 순서와 맞다. 결함: S1 장애가 "멈춤" 글자로만 보이고 선이나 상자 모양이 바뀌지 않는다. 자막이 길어 audit에서 화면 맞춤 78%로 줄었다.

**b.html**: `LTT.diagram` 격자와 `player` 단계 재생을 썼다. 다만 주인공이 그림이 아니라 아래 `rf-row` 텍스트 표다. audit도 그림이 화면의 11~15%뿐이라고 지적했다. 리더 장애 뒤 S2가 후보가 되는 흐름은 스토리보드와 맞고, 단계마다 서버 상태를 한 줄씩 바꾸는 방식은 쓸 만하다.

**c.html**: `LTT.diagram` 5노드 + `send` 패킷 + `player` 단계 재생으로 그림이 주인공이다. 흐름 도식 방식은 이 중 가장 맞다. 결함: S1 장애가 그림에 없고(`hot`만 있음), 역할·term·로그 칸이 그림에 없다. 그래서 "정리" 단계에서 무엇이 커밋되었는지 그림만으로는 안 보인다. audit: 그림 21%.

**d.html**: 커스텀 SVG. 결함이 크다. 첫 상태에 리더가 없고(`fresh`가 전부 팔로워), 죽은 리더가 S1이 아니라 살아 있는 S1이 후보가 되어 "리더가 죽고 다른 팔로워가 나선다"는 메커니즘이 어긋난다. S4는 처음부터 죽어 있어 장애 흐름이 이중이다.

## 가져올 것

- 골격: c의 `LTT.diagram` 5노드 펜타곤 배치(`cols 5, rows 3`)와 `player` 단계 재생, `send` 패킷. 부품 표의 "박스와 화살표"에 맞는다.
- 상태: a의 상자 정보(역할·term·로그 칸)를 축약해 쓴다. 그림 아래 5칸 상태 띠(서버별 역할·term·로그)로 두어, 그림이 주인공인 채로 상태를 보인다.
- 순서: a의 비트 순서와 자막 문장을 줄여 쓴다.
- 과반: a의 "과반 3/5" 문구를 자막과 `LTT.expect`에 둔다.

## 최종 방향

**그림의 뼈대**: 서버 5대를 펜타곤으로 놓고(S1 위, S2·S3 가운데 높이, S4·S5 아래) 모든 쌍을 점선으로 잇는다. 패킷은 메시지가 실제로 가는 선을 따라 움직인다. 그림 아래에 5칸 상태 띠(역할 · term · 로그)를 둔다.

**비트별 움직임**(순서 = 생성 순서):
1. S1이 리더(term 3). S1이 S2~S5에 heartbeat 패킷을 보낸다. 띠: S1 리더, 나머지 팔로워, 로그 1–6 커밋.
2. S1 멈춤. 띠에서 S1이 "멈춤"으로 바뀐다. 패킷이 멈춘다.
3. S3의 timer가 끝나 후보가 된다. term 4, 자기 표 1. S3이 강조된다.
4. S3이 RequestVote 패킷을 S2·S4·S5에 보낸다.
5. S2, S4가 표(초록 패킷)를 준다. 띠에 "3/5 → S3 리더".
6. S3이 heartbeat를 보낸다. 나머지는 팔로워(term 4).
7. 클라이언트 요청이 S3에 닿는다. S3 로그에 index 7 "미커밋"이 붙는다.
8. S3이 AppendEntries로 S2·S4에 index 7을 복제한다. 띠는 "미커밋" 그대로다.
9. S2, S4의 저장 응답(초록 패킷)이 S3에 닿는다. S3 포함 3/5 → index 7 "커밋".
10. S3이 commitIndex 7을 실은 heartbeat를 보낸다. S2·S4가 커밋해 적용한다. S5는 따라잡는 중으로 남는다.

**조작**: 없음(재생·다시 보기 단계 재생). 이 장면은 메커니즘 설명이라 손잡이를 두지 않는다.

**화면에 얹을 글**: 자막은 단계마다 한 문장. 제목은 "과반수 3/5가 리더를 뽑고 항목을 커밋한다". 요약 문장은 "선출도 커밋도 과반수(5대 중 3대)로 정한다". 용어는 `{{과반수}}`, `{{리더}}`, `{{커밋}}`, `{{임기|term}}`으로 풀어 둔다.
