# Raft 합의 — 리더 선출과 로그 복제 개요 스토리보드

## 독자가 말할 수 있어야 하는 한 문장
"Raft는 임기(term)마다 과반 투표로 리더 한 명을 뽑고, 리더가 로그를 복제해 과반이 저장하면 커밋하므로, 노드 일부가 죽어도 합의된 값이 사라지지 않는다."

## 인과 사슬
1. 팔로워가 election timeout(무작위, 예: 150–300ms) 안에 리더의 heartbeat를 못 받는다.
2. 그 팔로워가 term을 +1 하고 후보(candidate)가 되어 자기에게 투표한 뒤 RequestVote를 보낸다.
3. 각 노드는 term당 한 표만 준다. 후보 로그가 자기 것만큼 최신이어야 표를 준다.
4. 과반 표를 얻으면 리더가 되고 즉시 heartbeat(빈 AppendEntries)로 권위를 알린다.
5. 클라이언트 쓰기는 리더 로그에 먼저 append(미커밋) → AppendEntries로 팔로워에 복제한다.
6. 리더 포함 과반이 저장하면 commitIndex가 전진하고, 상태 기계에 적용한 뒤 클라이언트에 응답한다.
7. 이후 AppendEntries로 commitIndex가 팔로워에 전해져 팔로워도 적용한다.

## 화면에 꼭 보일 것
- 5노드 클러스터(노드별 term, 역할, 로그 칸).
- 투표 메시지와 득표 수 대 과반 기준선.
- 리더 로그의 항목 칸(미커밋/커밋 구분), 팔로워별 복제 진행.
- 강조점 하나: "과반(quorum)" — 선출과 커밋이 같은 문턱을 쓴다.

## 생성 순서 (틀리기 쉬운 곳)
- term 증가가 먼저, 투표 요청은 그 다음이다. 리더는 선출 뒤에야 존재한다.
- 항목은 리더 로그에 먼저 생기고(미커밋), 팔로워에 복제된 뒤, 과반 확인 후에야 커밋 표시가 된다. 커밋은 복제의 결과이지 전제가 아니다.
- 팔로워의 commitIndex 갱신은 리더보다 늦다.

## 사실 점검표
- 과반 = floor(N/2)+1. N=5 → 3, N=4 → 3, N=3 → 2. 5노드는 2대 장애까지 허용(5−3=2).
- 후보의 자기 투표도 득표에 포함한다. 5노드에서 후보 1 + 타 노드 2표 = 3 → 당선.
- 노드당 term당 최대 1표. 같은 term에 두 리더는 있을 수 없다(과반 두 개는 반드시 겹침).
- 표가 갈려 과반이 없으면(예: 2:2:1) 해당 term은 리더 없이 끝나고, 무작위 timeout 후 term+1로 재선거한다.
- 손 계산 예: 리더 L, 팔로워 F1–F4. 항목 x 복제 시 L(1)+F1+F2 ack = 3 ≥ 3 → 커밋. F3, F4가 늦어도 커밋은 유효하다. ack가 L+F1 = 2면 아직 미커밋.
- 이전 term의 항목은 개수만 세어 커밋하지 않는다. 현재 term의 항목이 과반 복제될 때 함께 커밋된다.
- term은 단조 증가한다. 더 큰 term을 본 리더는 즉시 팔로워로 물러난다.

## 흔한 오해와 깨는 순간
- 오해: "리더가 쓰기를 받으면 모든 팔로워가 저장해야 커밋된다" 또는 "리더가 로그에 쓰면 곧 커밋이다."
- 깨는 순간: 5노드 중 2대가 끊겨도 3대가 저장하면 커밋된다. 반대로 리더만 저장하고 죽으면(1/5) 항목은 미커밋이라 새 리더가 덮어쓸 수 있다.

## 비트
1. 평시: 리더 하나가 heartbeat를 보내고 팔로워는 조용하다.
2. 리더 장애: heartbeat가 끊기고 한 팔로워의 timeout이 먼저 끝난다.
3. 선출: term이 오르고 RequestVote가 나가며 3표째에 과반선을 넘어 새 리더가 선다.
4. 쓰기 복제: 새 항목이 리더에 미커밋으로 생기고 팔로워로 퍼진다.
5. 커밋: 3번째 저장 ack에서 항목이 커밋으로 바뀌고, 늦은 노드가 있어도 유효하다.
6. 선택 연결: 선출과 커밋이 둘 다 과반을 쓰므로 노드 수와 허용 장애 수를 보고 합의 기반 저장소를 고른다(홀수 노드 권장).
