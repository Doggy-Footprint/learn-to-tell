# 스토리보드: 가비지 컬렉션 방식 (contrast)

## 독자가 말할 한 문장
"참조 카운팅은 '나를 가리키는 수'가 0이어야 회수하므로 서로를 가리키는 고립된 순환은 영영 남고, mark-and-sweep은 루트에서 도달 가능한지만 보므로 같은 순환도 회수한다. 그래서 누수 진단은 '이 객체가 루트에서 닿는가'를 먼저 묻는다."

## 인과 사슬
1. 같은 코드가 객체 A, B를 만들고 A.peer=B, B.peer=A로 서로 가리키게 한 뒤 바깥 변수 x, y를 해제한다.
2. [참조 카운팅] 회수 조건은 각 객체의 카운트 == 0. 해제 후에도 A, B는 서로 한 개씩 가리키므로 카운트가 1에서 멈춘다 -> 회수 트리거가 영영 안 온다 -> 힙에 남는 누수.
3. [mark-and-sweep] 회수 조건은 mark 단계에서 표시되지 않음. 루트(전역·스택)에서 출발해 닿는 객체만 표시한다. A, B는 루트에서 닿지 않아 표시 안 됨 -> sweep이 해제.
4. 즉 두 방식의 차이는 "누가 나를 가리키는가(국소 개수)" 대 "루트에서 닿는가(전역 도달성)"이다. 순환은 국소 개수는 올리지만 도달성은 올리지 못한다.
5. 진단 함의: 두 방식의 누수 모양이 반대다. 참조 카운팅 런타임의 누수는 루트에서 경로가 없는데 retainer(붙잡는 쪽)가 서로뿐인 순환. tracing 런타임의 누수는 루트에서 경로가 있는 채로 의도치 않게 붙잡힌 객체(예: 계속 자라는 전역 캐시, 해제 안 된 리스너).

## 화면에 꼭 보여야 할 것
- 두 런타임에서 동일한 A↔B 순환과, 바깥 변수 x, y 해제 시점.
- 객체별 참조 카운트(참조 카운팅 쪽)와 mark 표시 여부(mark-and-sweep 쪽).
- 힙 스냅샷/프로파일러 시점의 retainer 목록: 객체마다 "누가 붙잡고 있는가"와 루트까지의 경로 유무.
- 강조점 하나: 해제 직후 A, B의 상태 -- 카운트는 1(남음) vs 미표시(회수).

## 생성 순서 (틀리기 쉬움)
- 객체 생성 -> 변수 연결 -> 객체끼리 연결 -> 변수 해제 순서. 순환은 변수를 해제하기 전에 이미 완성돼 있다.
- 카운트는 연결이 늘 때 오르고 해제 때 내린다. A: 1(x) -> 2(B.peer) -> 해제 후 1. B도 같다.
- mark-and-sweep은 반드시 mark(루트에서 도달 객체 표시)가 먼저, sweep(표시 안 된 것 해제)이 나중. sweep이 먼저 보이면 안 된다.
- 회수는 해제 즉시가 아니라 GC 사이클이 돌 때 일어난다(참조 카운팅은 0이 되는 즉시, tracing은 다음 사이클).

## 사실 점검표 (손 계산)
- 연결 직후: A 카운트 = x + B.peer = 2, B 카운트 = y + A.peer = 2.
- x 해제 -> A = 1. y 해제 -> B = 1. 둘 다 0이 아니므로 회수 안 됨. 루트 변수에서 출발하는 경로는 0개.
- 비교용: 순환 없이 x -> A 하나만 있고 x 해제 시 A = 1 -> 0, 즉시 회수. 순환이 있어야만 남는다.
- mark 결과: 루트 집합 {x, y 해제됨} 에서 도달 객체 0개 -> 표시 0, sweep 대상 2개(A, B).
- 부호·방향: 카운트는 "들어오는" 참조 수이지 나가는 참조 수가 아니다. A.peer=B는 B의 카운트를 올린다(A가 아님).
- 순환이 있어도 tracing GC에서는 누수가 아니다. 반대로 순환이 없어도 루트에서 닿으면 누수다.
- 실제 런타임: CPython은 참조 카운팅에 순환 탐지 보조 GC를 더하고, JVM·V8·Go는 tracing 계열. "참조 카운팅은 순환을 절대 못 푼다"는 순수 참조 카운팅에 한한 말이다.
- 스냅샷은 정지 시점의 한 장이다. V8 힙 스냅샷은 취득 전 GC를 돌리므로 도달 불가 객체는 보통 보이지 않는다.

## 흔한 오해와 깨는 순간
- 오해: "순환 참조가 있으면 어떤 런타임에서든 메모리 누수다."
- 깨는 순간: 같은 A↔B 순환을 두 런타임에 나란히 놓고 x, y를 해제하면, 한쪽은 카운트 1로 남고 다른 쪽은 표시 안 됨으로 사라진다. 이어서 tracing 쪽에서 순환 없는 객체가 전역 캐시를 통해 루트 경로로 붙잡혀 남는 모습을 보여 "누수 = 순환"이 아니라 "누수 = 회수 조건이 충족 안 됨"임을 드러낸다.

## 비트
1. 같은 코드가 A↔B 순환을 만들고 x, y로도 가리킨다: 카운트가 둘 다 2.
2. x, y를 해제한다: 카운트가 1로 내려가지만 0은 아니다.
3. 참조 카운팅 쪽 스냅샷: A, B의 retainer가 서로뿐이고 루트 경로가 없다 -- 남아 있다.
4. mark-and-sweep 쪽: 루트에서 출발한 표시가 A, B에 닿지 않고, sweep이 둘을 치운다.
5. tracing 쪽의 진짜 누수: 순환 없는 객체가 전역 캐시에서 루트 경로로 붙잡혀 남는다.
6. 진단 질문이 정해진다: 루트에서 경로가 있나(있으면 그 경로의 첫 retainer를 끊는다), 없으면 순환 retainer를 끊거나 약한 참조로 바꾼다.
