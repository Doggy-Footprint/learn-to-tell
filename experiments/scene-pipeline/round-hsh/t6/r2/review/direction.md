# direction

## 초안 점검
**a** (contrast, diagram 두 개 + 각자 player): 뼈대는 x,y→A↔B 그래프를 양쪽에 같게 놓고 단계마다 강조만 바꾼다. 카운트는 아래 문자열 한 줄로만 보이고 그림 안에서 숫자가 오르내리지 않는다. 사실은 맞다(2→1, mark 0개, sweep). 두 쪽 player가 따로라 같은 순간을 나란히 못 본다. 객체 생성 전에 변수가 이미 그려져 순서가 흐리다. tracing 쪽 진짜 누수(비트 5)가 없다.
**b** (rc/ms 비대칭 그림): 순서가 "x→A,y→B 먼저, 그다음 peer"는 맞지만 ms 쪽에 변수 x,y가 없어 같은 코드라는 비교가 깨진다. 카운트는 문구뿐이고 비트 5가 없다. 화면 결함은 audit 권고 shrunk(86%).
**c** (opacity로 생성 순서를 보임, 카운트 `counts()` 계산, retainer 줄): 가장 충실하다. 카운트를 incoming으로 계산하고 retainer 문구를 단계마다 바꾼다. 하지만 "x,y 해제 전 retainer에 루트 경로 있음"과 해제 후 대비는 좋은데 비트 5 없음, 두 player가 따로 돈다. 결함 코드: 없음(audit 0건).
**d** (LTT.expect로 손 계산 검증, 루트 노드 + 변수 노드를 생성 순서대로 나타냄): 객체 생성→x→y→A.peer→B.peer→해제 순서가 가장 정확하다. 카운트는 캡션 문장에만 있고 숫자가 그림에 안 붙는다. 8단계라 길고 비트 5가 없다.

## 가져올 것
- d: 생성 순서(객체→변수→A.peer→B.peer→해제)와 `LTT.expect` 손 계산 검증, 루트 프레임 개념.
- c: 단계별 retainer 문구, 카운트를 연결 목록에서 계산하는 방식.
- a: 양쪽에 같은 그래프를 놓는 대비 구도.
- 새로 만든다: 하나의 stepper로 두 패널을 동시에 움직임, 노드 안 카운트 배지, 비트 5의 전역 캐시 누수.

## 최종 방향
뼈대: 한 화면에 같은 힙 그림 두 개(참조 카운팅 / mark-and-sweep)를 나란히 두고 stepper 하나가 둘을 같은 순간으로 이끈다. 각 그림은 왼쪽 "루트" 틀(x, y, 전역 캐시) 안의 변수와 오른쪽 객체 A, B(, C)로 구성한다. 객체 상자 안에 카운트 배지(왼쪽)나 표시 배지(오른쪽)가 직접 붙는다.
비트: ① A, B가 생긴다(카운트 0) ② x→A, y→B가 그려져 1,1 ③ A.peer=B가 그려져 B=2 ④ B.peer=A가 그려져 A=2(순환 완성) ⑤ x,y 해제: 변수와 선이 흐려지고 카운트가 1,1로 내려감 / 오른쪽은 루트에서 닿는 길이 0개 ⑥ GC 사이클: 왼쪽은 0인 객체가 없어 아무 일 없음, 오른쪽은 루트에서 mark가 번쩍이지만 A,B에 안 닿음 ⑦ 왼쪽 A,B는 누수 표시로 남고 오른쪽 sweep이 A,B를 치움 ⑧ 오른쪽에 순환 없는 C가 전역 캐시에서 붙고 mark가 C에 닿아 남음: 누수 모양이 반대임.
조작: stepper(이전/다음/반복 재생). 글: 패널 아래 한 줄 상태(카운트·retainer), 단계 캡션, 마지막 캡션에 진단 질문("루트에서 경로가 있나?").
