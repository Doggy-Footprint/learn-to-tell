# 스토리보드: 가비지 컬렉션 방식 (contrast)

## 독자가 말할 한 문장
"참조 카운팅은 '나를 가리키는 화살표가 몇 개인가'를 세므로 서로 가리키는 순환 쌍은 영원히 0이 안 되어 남고, mark-and-sweep은 '루트에서 닿는가'를 보므로 같은 순환 쌍도 루트가 끊기면 회수한다. 그래서 힙 프로파일러에서 같은 코드가 한쪽은 계단식 증가, 한쪽은 톱니로 보인다."

## 인과 사슬
1. 코드가 객체 A, B를 만들고 A.peer=B, B.peer=A로 서로 참조하게 한 뒤, 루트(지역변수)가 A를 놓는다.
2. 참조 카운팅: 루트 해제로 A의 카운트가 2→1로만 줄고(B가 아직 A를 가리킴), B는 1(A가 가리킴)로 그대로. 0이 아니므로 해제 안 됨.
3. 아무도 도달 못 하는데 메모리는 남는다. 이 쌍이 반복 생성되면 힙이 계속 오른다 → 누수.
4. mark-and-sweep: GC 시점에 루트에서 출발해 도달 가능한 것만 mark. A, B는 mark 안 됨 → sweep에서 둘 다 회수. 순환은 판단에 영향이 없다.
5. 진단: 힙 스냅샷 두 장을 비교해 "증가한 클래스·개수"를 보고, 보유 경로(retainers)가 객체끼리 순환뿐이면 카운팅형 누수, 루트까지 이어지면 도달 가능한 진짜 참조 누수.

## 화면에 꼭 보일 것
- 같은 코드, 같은 입력을 두 런타임에 넣은 대비(좌 카운팅 / 우 mark-and-sweep). 각 쪽에 객체 A, B, 루트, 화살표, 카운트 또는 mark 표시.
- 각 쪽의 힙 사용량 시계열(프로파일러 타임라인)과 스냅샷 객체 목록(클래스, 개수, retained size).
- 강조점 하나: 루트가 끊긴 뒤 A, B에 남는 화살표 — 카운트는 "1, 1"로 남고, mark는 "도달 불가"로 끝난다.

## 생성 순서 (틀리기 쉬운 곳)
1. 객체가 먼저 생긴다: A 생성(rc=1, 루트만), B 생성(rc=1).
2. 그다음 A→B 연결로 B의 rc=2, B→A 연결로 A의 rc=2. (참조를 만든 뒤에야 카운트가 오른다. 이 시점에 순환이 완성된다.)
3. 마지막에 루트가 A, B에서 손을 뗀다: rc는 각각 2→1. 이때 비로소 "도달 불가인데 카운트 1"이 생긴다.
4. 카운트는 해제 사건마다 즉시 갱신되지만, mark-and-sweep의 mark/sweep은 힙이 임계에 닿을 때(GC 시점) 뒤늦게 일어난다. 따라서 mark 쪽 힙은 해제 직후엔 안 줄고 GC 시점에 한꺼번에 떨어진다(톱니).
5. 반복 루프에서 쌍이 쌓이는 순서: 쌍1, 쌍2… 카운팅 쪽은 쌓인 채 남고, mark 쪽은 GC 때 마지막으로 쓰인 쌍들이 한꺼번에 사라진다.

## 사실 점검표
- 카운트 손계산: 루트 변수 a가 A를 가리키면 A=1. A.peer=B → B=1. B.peer=A → A=2. 루트가 a를 놓으면 A=1. B는 루트가 안 쥐었으니(생성 직후 b도 지역변수라면 b 해제 시 B=2→1) 최종 A=1, B=1. 둘 다 0이 아님.
- 수치 예: 객체 하나 512 KB, 쌍 하나 1 MB(2×512 KB), 100번 반복 → 카운팅 쪽 누수 100 × 1 MB = 100 MB. 쌍당 1 MB 증가가 선형으로 쌓임(계단/기울기), 반복 수에 비례.
- mark-and-sweep 쪽 예: GC 임계 16 MB라면 약 16쌍(16 MB ÷ 1 MB)마다 GC가 돌아 기준선(예: 4 MB)으로 복귀. 최대 약 20 MB, 최저 약 4 MB 톱니. 기준선은 오르지 않는다.
- 화살표 방향: 카운트는 "들어오는" 참조 수, mark는 루트에서 "나가는" 화살표를 따라간다. 방향을 뒤집지 않는다.
- 카운팅의 장점도 사실이다: 해제가 즉시라 정지 시간이 짧고 예측 가능. mark-and-sweep은 GC 정지(pause)가 생긴다. 승패가 아니라 대비로 그린다.
- 실제 런타임: CPython은 카운팅에 순환 감지기를 덧붙여 순환을 결국 회수한다(gc 모듈). 순수 카운팅 누수는 순환 감지가 없을 때의 모델이라고 명시한다.

## 흔한 오해와 깨는 순간
- 오해: "순환 참조가 있으면 어떤 GC든 누수다" 또는 반대로 "GC가 있으니 누수는 없다".
- 깨는 순간: 같은 A↔B 순환이 mark-and-sweep 쪽에서는 루트를 끊자마자 mark 단계에서 아무 표시도 못 받고 sweep으로 사라진다. 그러나 한편 같은 mark 쪽 힙에서 전역 캐시가 A를 붙잡고 있으면 루트에서 닿으므로 회수되지 않는다 — 누수 여부는 "순환인가"가 아니라 "루트에서 닿는가"로 결정된다.

## 비트
1. 같은 코드 두 런타임: 객체 A, B가 서로 가리키고 루트가 둘을 쥐고 있다(카운트 A=2, B=2 아님: 루트 1 + 상대 1, 연결 후 값 확인).
2. 루트를 놓는 순간: 카운팅은 1, 1로 줄다 멈추고, mark 쪽은 아직 아무 일도 없다 — 즉시 vs 지연의 차이를 알아차린다.
3. mark-and-sweep GC 시점: 루트에서 닿는 것만 표시되고 A, B는 표시 없이 회수된다.
4. 100번 반복: 프로파일러 타임라인에서 카운팅은 +1 MB씩 올라 100 MB, mark는 4~20 MB 톱니.
5. 스냅샷 비교: 카운팅 쪽은 A, B 클래스 개수가 100쌍(200개)으로 늘고 retainer가 서로뿐 — 루트로 가는 경로가 없음을 읽어낸다.
6. 반전: mark 쪽에서도 전역 캐시가 A를 쥐면 스냅샷 retainer가 루트까지 이어지며 누수가 된다. 진단 질문은 "누가 붙잡고 있나".
