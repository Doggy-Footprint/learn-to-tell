# Phase A — 블라인드 관점 (plan.md·ADR·실험 보고서를 읽기 전)

읽은 것: `bench/v1-results.md`, `archive/v1`의 SKILL.md·compare1 index·생성 시간 handoff, `bench/topics.md`,
`bench/m1/gen/gen-common.md`, 세 주제의 `prompt.md`·`baseline-prompt.md`·`lesson.js`·`baseline.html`·`ltt-log.jsonl`,
skill 수업 스크린샷(sheet desktop/mobile), baseline을 직접 찍은 화면(desktop 1100/1280, mobile 390).

## 1. v1이 실패한 이유를 내가 읽은 대로

- v1-results가 기록한 실패는 **품질이 아니라 비용·시간**이다. 기준선(skill 없이 "학습 자료 만들어 달라") 대비 토큰 8.2배, 생성 16–35분.
  사용자 판정은 "그림 품질은 괜찮다".
- 시간의 58%가 audit·검증 반복이었다. 반복을 만든 것은 레이아웃 결함(넘침·겹침·작은 글자), kit 사용 형식 오류, 검증 불가 항목.
- **빠진 측정**: v1이 8배 비용으로 기준선보다 *더 나은 학습*을 만들었는지는 한 번도 재지 않았다.
  블라인드 쌍 비교(audit5-check)는 kit 버전끼리였지 v1 대 기준선이 아니었다. 기준선은 "검토·렌더링 확인을 하지 않았다"고만 적혀 있다.
  그래서 "v1의 추가 비용이 무엇을 샀는가"라는 질문의 답이 기록에 없다.

## 2. 내가 이 문제를 푼다면

전제: 기준선(일반 agent가 HTML 한 장을 3분·~60k 토큰에 쓴 것)이 이미 "읽을 만한 자료"를 만든다.
skill이 기준선 위에 더할 수 있는 가치는 화면 그리기가 아니라 다음 네 가지다.
1. 진단: 사용자가 모르는 결정 변수와 오개념을 찾는 것(일반 요청은 이걸 하지 않는다).
2. 교수 설계: 오개념을 겨냥한 예측→공개, 결정 변수를 직접 움직이는 시뮬레이션 1–2개, 서술형 확인.
3. 사실·수치 정확성: 숫자와 주장 검산.
4. 원래 작업과 지식 map으로 결과를 돌려주는 것.

그래서 내 방향은 **"agent가 HTML을 직접 쓰고, skill은 얇은 교수 설계 지시 + 작은 보조물 + 한 번만 도는 값싼 검사"** 다.
- 생성: agent가 자기 HTML을 쓴다(기준선과 같은 방식). skill은 진단 결과, 오개념, 꼭 들어갈 요소(예측→공개, 결정 변수 시뮬레이션,
  오개념 정면 대조, 작업 적용 절, 서술 퀴즈)를 짧은 체크리스트로 준다.
- 보조물: 선택적으로 쓰는 작은 CSS 한 장 + 퀴즈 결과·예측 이벤트를 기록하는 작은 스크립트(map 연결용). 그리기 엔진은 두지 않는다.
- 검사: 헤드리스 브라우저로 두 폭에서 한 번 열어 결정적 검사(JS 오류, 가로 넘침, 요소 겹침, 빈 버튼)만 하고, 걸리면 1회 고친다.
  사실·수치는 별도 서브에이전트 1회(또는 생략 가능)로 검산한다. 반복 회차 상한 1.
- 이해 확인은 페이지가 아니라 **대화**에서 서술형으로 한다(agent가 채점할 수 있는 유일한 곳).
- 판단 기준: 기준선 대비 "같은 비용대(≤2배)에서 측정 가능한 학습 품질 우위"가 없으면 skill의 생성 단계는 기준선 + 지시문으로 충분하다.

이 방향의 위험: 레이아웃 결함은 다시 생긴다(v1에서 본 것). 대응은 "결함을 0으로 만드는 반복" 대신 "치명 결함만 결정적으로 잡고,
나머지는 감수"로 기준을 낮추는 것이다. 기준선 화면에서도 결함이 보이지만(아래), 학습을 막는 수준은 아니었다.

## 3. skill 경로 수업 대 기준선 관찰

### 공통
- 크기: skill `lesson.js` 17–23KB, 기준선 HTML 19–34KB. **agent가 써 내는 분량은 거의 같다.** spec이라서 출력이 작아지지 않았다.
  skill 수업은 이 밖에 미리 빌드된 runtime(약 3.9MB: elk 1.4MB, 폰트 1.5MB, katex 등)과 정적 서버가 필요하다. 기준선은 파일 하나다.
- 본문 분량: 화면에 보이는 한글 음절 수가 기준선이 1.6–1.8배(skill 1,772–2,192 / 기준선 2,911–3,805).
  skill 수업 20–21장면이지만 장면당 글이 1–3문장이다.
- 퀴즈: skill은 선택·수치·순서·분류 자동 채점만 있다. **서술형이 없다.** 기준선은 서술형 자기 점검(답 접힘)이 있지만 채점은 없다.
- 입력 조건이 다르다: skill prompt에는 진단 결과(사다리·오개념)가 들어가고, 기준선 prompt에는 상황·배경만 있다.
  기준선은 오개념을 모르고 썼는데도 세 주제 모두 오개념을 직접 다룬다(attacker Q1, supply Q1, UI "장식을 더하는 게 아니라").

### attacker-moves-second
- 기준선: 정적 글(스크립트 0), 표 5개, 코드 예시. 방어 계열과 실제 이름(Spotlighting, PromptGuard, StruQ/SecAlign, MELON),
  lethal trifecta, 읽기 전용·권한 축소·CaMeL류 설계, 벤더 평가 체크리스트, 서술 문항 5개. **사용자의 실제 결정(어떤 방어를 믿고 어떻게 설계할지)에 바로 쓰인다.**
- skill: 예측·비교·탐색·단계 장면이 있고 상호작용은 많다. 그러나 4절 중 1절을 `1-(1-p)^n` 독립 시행 모델에 쓴다.
  논문의 핵심(적응성)과 다른 메커니즘이고, 수업도 "실제로는 이보다 빨리 오른다"며 스스로 단서를 단다. 막대 값은 전부 "가정 값".
  설계 권고는 마지막 장면 한 문장뿐이다.
- 화면 결함: 예측 장면(#6)에서 끌어 놓을 점이 처음부터 정답 위치(63%)에 있다. 방법 그래프의 노드 글자가 단계에 따라 바뀌지 않는다
  (1단계 "gradient" 설명인데 노드는 "사람 red-teamer" / "손실·기울기"로 고정). #14 예측은 "A 0.5% vs B 30%"를 묻는데 그림은 무관한 막대.
  #15 체크리스트 장면의 그림도 무관한 막대. 그래프가 화면의 작은 부분만 쓴다. 퀴즈 장면은 왼쪽 절반이 빈 회색 판이다.
  모바일: 비교 장면 막대 라벨 겹침, 공개 뒤 카드 첫 줄 잘림.

### global-supply-chain
- 기준선: 스크립트 0, 상자·선으로 그린 개념도(축척 무시, 지리 부정확). 대신 정기선/벌크/탱커 구분, 얼라이언스, 계약 형태·인코텀즈,
  파나마 갑문·흘수 제한, 조달 체크리스트, 리드타임·추가 재고 계산 예시. "읽는 데 약 40분"이라 스스로 적어 분량 목표를 넘는다.
- skill: 실제 세계 지도 위 수에즈/희망봉 경로, chokepoint 단계, 왕복일·필요 선박 수 모델(검산 일치), bullwhip(Chen et al. 2000 하한식),
  안전재고 √L, 탐색 슬라이더. **시각화와 수치 모델은 skill 쪽이 낫다.**
  내용 결함: 운임 모델이 가동률 100%를 넘는 값(1.07)을 내고, "100%에 가까워지면 가파르게 오른다"는 설명과 달리 단순 지수함수다.
  첫 예측(운송 수단 단가)은 로그 축 막대가 처음부터 보여 답이 드러난다. 정답 "100배 넘게"가 agent의 가정 값에서 나온다.
  `ltt-log.jsonl`에서 마지막 check가 `exit 1, check:1`인 채로 sheet로 넘어갔다(검사 오류를 남긴 채 끝냄).

### polished-ui-components
- 기준선: **실제 HTML/CSS로 만든 관리자 표에 원리별 CSS를 켜고 끄는 실험실**, 좋은 예/나쁜 예 쌍, 토큰 CSS, 13항목 진단 체크리스트,
  고치는 순서. 주제와 매체가 일치한다. 결함: 모바일에서 "모두 켜기" 뒤 표가 가로로 넘친다(scrollWidth 548 > 390), 한글 이름이 글자 단위로 꺾인다.
- skill: 폼이 회색 직사각형 자리표시로 그려진다(글자 없음). 버튼은 라벨이 상자 밖에 붙은 파란 사각형, 빈 상태는 점선 사각형,
  포커스 링 장면은 그림이 없다. **"세련된 UI"를 배우는 수업이 세련되지 않은 추상 도형으로 그려진다.** 오개념(장식)을 보여줄 `deco` 파라미터가
  있지만 어느 장면도 켜지 않아 그림자 대비가 한 번도 나오지 않는다. 타입 스케일 예측(#6)에서 막대 라벨 "H1 21"이 처음부터 보여 답이 드러난다.
  대비비·타입 스케일 수치는 정확하다(#a0a0a0 2.6:1, #767676 4.54:1).

### 종합 판단(Phase A 시점)
- 정확성: 두 쪽 모두 큰 사실 오류는 못 찾았다. skill 쪽은 수치 검산이 붙어 계산 실수가 없지만, 많은 값을 "가정"으로 처리해 실제 수치 정보가 적다.
- 상호작용: skill이 일관되게 많다(예측·슬라이더·단계). 기준선은 주제에 따라 0(두 개) 또는 매우 좋음(UI).
- 학습·결정 유용성: 내 판단으로는 기준선이 3개 중 2개(attacker, UI)에서 낫고, supply는 시각화는 skill, 실무 내용은 기준선이 낫다.
- skill 쪽 결함의 상당수는 **runtime이 아니라 내용 설계**다(정답 노출, 그림-질문 불일치, 주제와 맞지 않는 매체, 오개념 대조 누락).
  runtime 결함으로 보이는 것은 노드 라벨 고정, 모바일 카드 잘림, 그래프 크기, 빈 퀴즈 판 정도다.
- runtime이라는 구조가 직접 만든 한계: UI처럼 "실물 화면" 자체가 학습 대상인 주제를 표현할 수 없고, 지도·그래프 같은 정해진 그림 종류 밖으로 나가지 못한다.
