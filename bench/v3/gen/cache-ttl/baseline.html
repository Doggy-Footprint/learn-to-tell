캐시 TTL을 어떻게 정할까

상품 정보 API에 캐시를 붙이는 백엔드 개발자를 위한 학습 자료 · 30~40분

이 자료를 다 읽으면 할 수 있는 것
  • hit / miss / TTL / stale을 요청 흐름으로 설명한다.
  • "TTL을 늘리면 무엇이 좋아지고 무엇이 나빠지는지"를 숫자로 말한다.
  • 상품 정보의 필드별로 TTL을 다르게 잡고, 그 이유를 팀에 설명한다.
  • TTL만으로 부족할 때 쓰는 도구(무효화, stale-while-revalidate, jitter)를 안다.

1. 용어를 요청 흐름으로 이해하기

캐시는 "원본(DB나 다른 서비스)에서 가져온 응답을 잠시 보관해 두었다가, 같은 요청이 오면 원본을 거치지 않고 돌려주는 저장소"입니다. 보통 Redis나 서버 메모리를 씁니다.

GET /products/123
   │
   ▼
[캐시에 product:123 있나?]
   ├─ 있음, 아직 유효 ──▶ HIT  : 캐시 값 즉시 반환 (빠름, 원본 부하 0)
   └─ 없음 또는 만료 ──▶ MISS : 원본 조회 → 캐시에 저장(TTL 설정) → 반환
용어뜻상품 API에서의 예
Hit캐시에 유효한 값이 있어서 바로 응답1초 전에 누가 조회한 123번 상품을 또 조회
Miss캐시에 없거나 만료되어 원본까지 감처음 조회되는 상품, 또는 TTL이 지난 상품
Hit ratehit 수 ÷ 전체 요청 수90%면 원본은 요청 10개 중 1개만 받음
TTL (Time To Live)저장 후 유효하다고 간주하는 시간SET product:123 {...} EX 300 → 5분
Stale원본은 바뀌었는데 캐시는 옛 값을 들고 있는 상태가격이 9,900원 → 8,900원으로 바뀌었는데 캐시가 9,900원 응답

타임라인으로 보기 (TTL = 60초)

시각 0s 20s 45s 60s 61s 90s 요청 A B C D E 캐시 MISS HIT HIT (만료) MISS HIT 원본 조회 조회 가격 9,900 ─────────▶ 30s에 8,900으로 변경 응답 9,900 9,900 9,900(stale) 8,900 8,900

요청 C는 hit이라 빨랐지만 틀린 가격을 받았습니다. 30초에 바뀐 가격이 사용자에게 보이기까지 최대 TTL(60초)만큼 걸릴 수 있다는 뜻입니다.

핵심 한 줄: TTL은 "원본이 바뀐 뒤 사용자가 옛 값을 볼 수 있는 최대 시간"이다. (무효화를 따로 하지 않는 한)

2. TTL은 두 비용의 줄다리기

TTL 짧게 (예: 5초)TTL 길게 (예: 1시간)
Hit rate낮음높음
원본 부하큼작음
응답 신선도거의 최신최대 1시간 옛 값
캐시 메모리적게 씀많이 씀

숫자로 감 잡기 — 키 하나 기준

어떤 상품이 초당 r번 조회되고 TTL이 T초라면, 대략 TTL 한 주기마다 miss가 1번 납니다.

  • 원본 조회 횟수 ≈ 1 / (T + 1/r) 회/초  (≈ T마다 1번)
  • Hit rate ≈ rT / (1 + rT)

예) 초당 10번 조회되는 인기 상품:

TTLHit rate원본 조회/분
1초91%약 55회
10초99%약 6회
60초99.8%약 1회
600초99.98%약 0.1회
관찰 1 — 수익 체감: 인기 키는 TTL 몇 초만으로 hit rate가 이미 90%를 넘습니다. 1분 → 10분으로 늘려도 부하 절감은 미미한데, stale 위험은 10배가 됩니다.

관찰 2 — 롱테일: 하루에 몇 번 조회될까 말까 한 상품은 TTL 1분이면 거의 항상 miss입니다. 이런 키들은 TTL을 꽤 길게 잡아야 효과가 있습니다. 즉 "부하 절감 효과"는 TTL보다 트래픽 분포가 결정합니다.

Stale은 얼마나 생기나

데이터가 평균 U초마다 한 번 바뀐다면, hit 응답 중 stale 비율은 대략 T / (2U) 정도입니다 (T가 U보다 꽤 작을 때). 예: 가격이 하루(86,400초)에 한 번 바뀌고 TTL 5분이면 → 300 / 172,800 ≈ 0.17%. 그리고 stale 응답의 최대 지연은 언제나 T입니다.

즉 판단 질문은 두 개로 줄어듭니다.

  1. 최대 몇 초까지 옛 값을 보여줘도 괜찮은가? → TTL의 상한 (비즈니스가 정함)
  2. 원본이 버틸 수 있는 miss량은 얼마인가? → TTL의 하한 (인프라가 정함)

상한 ≥ 하한이면 그 사이에서 고르면 되고, 상한 < 하한이면 TTL로는 해결이 안 되니 6장의 도구가 필요합니다.

3. 직접 돌려보는 TTL 시뮬레이터

Hit rate
원본 조회
Stale 응답 비율

그래프: 가로축 TTL(로그 스케일). 초록 = hit rate, 주황 = stale 비율, 세로선 = 현재 TTL. 모델: 조회·변경이 무작위(포아송)로 일어난다고 가정한 근사치.

해 볼 것: ① 조회 빈도를 "초당 10회"로 두고 TTL을 늘려 보세요 — 초록선이 금방 천장에 붙습니다. ② 조회 빈도를 "시간당 1회"로 낮춰 보세요 — TTL을 크게 해야 초록선이 올라옵니다. ③ 변경 주기를 "1분"으로 줄여 보세요 — 같은 TTL에서 주황선이 치솟습니다.

4. TTL 결정 절차 (실전 체크리스트)

  1. 데이터를 필드 단위로 나눈다. 상품명·설명·이미지와 가격·재고는 바뀌는 빈도도, 틀렸을 때 피해도 전혀 다릅니다.
  2. 필드마다 "허용 가능한 최대 지연"을 기획/운영과 합의한다. "가격 변경이 반영되기까지 최대 몇 분이면 괜찮나요?"라고 물으세요. 이게 TTL 상한입니다.
  3. stale이 일으키는 피해를 확인한다. 보여주기만 하는가(상세 페이지), 돈이 오가는가(결제)? 돈·재고 확정 단계는 캐시를 읽지 않고 원본으로 재검증하는 것이 원칙입니다.
  4. 트래픽을 측정한다. 전체 QPS, 상위 키 집중도(상위 1% 상품이 트래픽 몇 %?), 원본이 감당 가능한 QPS. 이것으로 TTL 하한을 구합니다.
    예: 상품 조회 2,000 QPS, DB 허용 200 QPS → hit rate 90% 이상 필요.
  5. 상한 안에서 하한을 넘는 가장 짧은 값을 고른다. 애매하면 짧게 시작하세요. 늘리는 건 쉽고, 긴 TTL로 사고가 난 후 줄이는 건 늦습니다.
  6. 배포 후 지표로 조정한다. hit rate, 원본 QPS, p99 응답시간, "가격 불일치" 문의/에러 건수.

필드별 TTL을 쓰려면 캐시 키를 나누면 됩니다.

product:123:info   → EX 1800   (이름/설명/이미지)
product:123:price  → EX 60
product:123:stock  → EX 5

기본 패턴(cache-aside) 코드 스케치:

async function getProductInfo(id) {
  const key = `product:${id}:info`;
  const cached = await redis.get(key);
  if (cached) return JSON.parse(cached);          // HIT

  const info = await db.findProductInfo(id);      // MISS → 원본
  const ttl = 1800 + Math.floor(Math.random() * 300); // jitter (6장)
  await redis.set(key, JSON.stringify(info), 'EX', ttl);
  return info;
}

// 상품 수정 API에서
async function updateProduct(id, data) {
  await db.update(id, data);
  await redis.del(`product:${id}:info`);           // 무효화: 다음 조회 때 새로 채움
}

6. TTL만으로 부족할 때

① 명시적 무효화 (invalidation)

데이터를 바꾸는 쪽이 캐시 키를 지웁니다. 그러면 TTL은 "무효화가 실패했을 때의 안전망"이 되어 길게 잡아도 됩니다. 단, 변경 경로가 여러 개(관리자 페이지, 배치, 다른 팀 서비스)면 하나라도 빠뜨리면 TTL만큼 stale이 납니다. 그래서 무효화를 해도 TTL은 반드시 둡니다.

주의: "DB 갱신 → 캐시 삭제" 순서를 지키세요. 삭제 후 갱신하면 그 사이 조회가 옛 값을 다시 캐시에 넣을 수 있습니다.

② TTL jitter

배치로 상품 1만 개를 동시에 캐시에 채우면 정확히 TTL 후 1만 개가 동시에 만료되어 원본에 몰립니다. TTL에 ±10% 정도 무작위 값을 더해 만료 시점을 흩으세요.

③ 캐시 스탬피드 (thundering herd) 방지

초당 1,000번 조회되는 인기 상품의 키가 만료되는 순간, 원본 조회가 끝나기 전 들어온 수십~수백 요청이 모두 miss가 되어 DB로 갑니다. 대책:

  • 락/싱글플라이트: 한 요청만 원본을 조회하고 나머지는 기다렸다 그 결과를 씀.
  • stale-while-revalidate: 만료된 값을 일단 응답하고, 백그라운드에서 한 번만 갱신. "조금 옛 값 OK"인 데이터에 아주 효과적.

④ 소프트 TTL / 하드 TTL

값에 "갱신 권장 시각(soft, 예: 60초)"을 같이 저장하고 Redis TTL(hard)은 더 길게(예: 10분) 둡니다. soft가 지나면 응답은 캐시로 하되 비동기로 갱신, 원본이 죽었을 때도 hard까지는 서비스가 유지됩니다. 신선도와 장애 내성을 동시에 얻는 방법입니다.

⑤ 네거티브 캐싱

존재하지 않는 상품 ID 조회(잘못된 링크, 크롤러)도 매번 DB까지 갑니다. "없음" 결과도 짧은 TTL(예: 30초)로 캐시하세요.

⑥ HTTP 캐시 헤더 (CDN/브라우저)

Cache-Control: public, max-age=60, stale-while-revalidate=300

서버 캐시와 별개로 CDN·브라우저에도 캐시가 생깁니다. 이쪽은 서버가 지울 수 없는 경우가 많으니(특히 브라우저), 서버 내부 캐시보다 TTL을 짧게 잡는 게 안전합니다. 개인화된 응답에는 private 또는 no-store를 쓰세요.

7. 흔한 실수

  • 모든 키에 같은 TTL — 이름과 재고는 다른 데이터입니다.
  • 결제·주문에서 캐시된 가격/재고를 그대로 사용 — 표시용은 캐시, 확정은 원본.
  • TTL 없이 무효화만 의존 — 무효화 누락 시 영원히 stale.
  • hit rate만 보고 TTL을 계속 늘림 — 1분 이후 개선은 대부분 미미하고 stale만 늘어납니다.
  • 캐시가 죽었을 때를 고려 안 함 — hit rate 99%에 의존하던 DB는 캐시 장애 시 100배 부하를 받습니다. 원본 보호(타임아웃, 서킷 브레이커)도 필요합니다.
  • 지표 없이 배포 — hit/miss 카운터와 원본 QPS를 반드시 대시보드에 올리세요.

8. 확인 문제

Q1. TTL 5분, 가격이 12:00:00에 바뀌었다. 사용자가 옛 가격을 볼 수 있는 가장 늦은 시각은? (무효화 없음)

최대 12:05:00 직전까지. 11:59:59에 캐시가 채워졌다면 그 값은 12:04:59까지 유효합니다. TTL = 최대 지연.

Q2. 상품 A는 초당 50회, 상품 B는 하루 3회 조회된다. TTL 30초면 각각 hit rate는 대략?

A: rT = 1500 → 약 99.9%. B: 조회 간격(약 8시간)이 TTL보다 훨씬 길어서 거의 0%. B에게 캐시 효과를 주려면 TTL을 시간 단위로 해야 하고, 그만큼 stale 허용이 가능한 데이터인지 따져야 합니다.

Q3. 기획: "가격 변경은 즉시 반영돼야 해요." 그런데 DB는 캐시 없이는 못 버틴다. 어떻게?

TTL로는 상한(≈0)과 하한이 충돌합니다. 가격 변경 시 명시적 무효화(또는 새 값으로 덮어쓰기)를 하고, TTL은 안전망으로 수 분 정도 둡니다. 결제 단계에서는 원본 가격으로 재검증합니다. "즉시"가 정말 0초인지, "수 초 이내"면 되는지도 다시 합의해 보세요.

Q4. 매일 자정 배치로 전 상품 캐시를 워밍하고 TTL을 정확히 1시간으로 줬다. 무슨 일이 생길까?

매일 01:00에 전 상품이 동시에 만료되어 원본 부하가 급증합니다. TTL jitter를 넣어 만료를 분산하세요.

Q5. hit rate가 60%밖에 안 나온다. TTL을 늘리기 전에 확인할 것은?

트래픽이 롱테일인지(키가 너무 다양), 캐시 키에 불필요한 값(쿼리스트링 순서, 사용자 ID 등)이 섞여 같은 데이터가 다른 키로 저장되는지, 메모리 부족으로 eviction이 일어나는지 확인합니다. TTL이 원인이 아닐 때가 많습니다.

요약
  1. TTL = 옛 값을 보여줄 수 있는 최대 시간. 상한은 비즈니스가 정한다.
  2. TTL 하한은 원본이 감당 가능한 miss량이 정한다. 인기 키는 짧은 TTL로도 충분하다.
  3. 데이터를 필드별로 나누어 TTL을 다르게. 돈·재고 확정은 원본으로.
  4. 둘이 충돌하면 무효화, stale-while-revalidate, soft/hard TTL을 쓴다. jitter는 기본.
  5. 짧게 시작하고 지표를 보며 늘린다.
