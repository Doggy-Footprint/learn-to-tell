캐시 TTL은 어떻게 정하나: 원본 부하와 오래된 응답

상품 정보 API 앞에 캐시를 붙인다. TTL을 정할 때 따져야 할 것은 두 가지다. 원본(DB/서비스)에 가는 요청이 얼마나 줄어드나, 그리고 사용자가 받는 응답이 얼마나 오래된 것일 수 있나. 이 글에 나오는 트래픽 수치는 모두 예시값이다.

0. 복습: hit, miss, TTL

  • miss: 캐시에 값이 없거나 만료됨 → 원본에 요청 → 결과를 캐시에 넣고 "이 시점부터 TTL초 유효"로 표시.
  • hit: 유효한 값이 있음 → 원본에 가지 않고 바로 응답.
  • TTL과 만료 시점: 만료 시각 = 값을 채운 시각 + TTL. 마지막으로 읽은 시각이 아니다(일반적인 고정 TTL 기준). 만료 뒤 다음 요청이 올 때 비로소 miss가 나고 다시 채운다. 아무도 안 읽으면 만료돼도 원본 요청은 없다.

1. stale 응답의 나이: 최대 TTL

캐시에 담긴 값의 나이는 채운 순간 0이고, 시간이 지나면서 커지다가 TTL에 닿으면 만료된다. 원본의 가격이 채운 직후 바뀌었다면, 사용자는 최대 TTL초 동안 옛 가격을 본다. 아래는 요청이 끊임없이 들어오는 키에서 캐시 값의 나이다(톱니 모양).

stale의 최대 나이 = TTL. 비용은 "오래된 응답 한 번의 피해 × 그런 응답 수"다. 가격·재고처럼 틀리면 주문 오류로 이어지는 필드는 TTL을 짧게, 상품 설명·이미지처럼 덜 민감한 필드는 길게 잡을 수 있다. 바뀔 때 캐시를 지우는(무효화) 방식이 있으면 TTL은 안전망 역할만 한다.

2. hit 비율과 원본 요청 수

키 하나에 초당 λ개의 요청이 무작위로(포아송) 온다고 하자. 한 주기는 "miss 1번 → TTL 동안 hit → 만료 뒤 다음 요청이 올 때까지 평균 1/λ초 대기"다. 그래서

주기 길이 = T + 1/λ
원본 요청 수(초당) = 1 / (T + 1/λ)
hit 비율 = λT / (1 + λT)

아래 차트에서 λ를 바꿔 보라. 시간당 원본 요청 수를 TTL에 따라 그렸다.

오개념 점검: "TTL을 두 배로 늘리면 원본 요청이 절반이 된다"
λ=0.1(10초에 한 번), TTL 10→20초: 3600/(10+10)=180 → 3600/(20+10)=120. 절반(90)이 아니라 2/3이다. 만료 뒤 다음 요청을 기다리는 1/λ초는 TTL과 상관없이 매 주기 붙기 때문이다.
λT가 아주 크면(인기 키) 1/λ가 무시되어 거의 절반이 되지만, 그때는 원본 요청이 이미 아주 적다. λT가 아주 작으면(거의 안 읽는 키) TTL을 늘려도 거의 매번 miss다.
대신 TTL을 두 배로 하면 stale 최대 나이는 정확히 두 배가 된다. 이득은 덜, 비용은 그대로 늘어난다.

λ=0.1/초인 키의 TTL을 10초에서 20초로 늘렸다. 원본 요청 수는?

3. 요청 분포에 따라 TTL 효과가 다르다

실제 상품은 키가 많고 인기는 고르지 않다. 상품 1000개, 전체 초당 100요청(예시값)을 두 가지로 나눠 보자.

  • 균등: 모든 상품이 λ=0.1.
  • Zipf(s=1): i번째 인기 상품이 1/i에 비례. 소수 인기 상품이 대부분의 요청을 받는다.

전체 원본 요청 = 키별 1/(T+1/λᵢ)의 합.

TTL 10→20초에서 균등은 50→33.3(−33%), Zipf는 28.5→20.8(−27%). Zipf에서 인기 키는 이미 거의 다 hit이라 더 줄 것이 적고, 꼬리의 비인기 키는 TTL 안에 다시 읽히지 않아 계속 miss다. 그래서 Zipf 트래픽에서는 TTL을 늘려도 원본 감소 폭이 작다. TTL을 키우기 전에 "원본 요청을 실제로 만드는 키가 어느 쪽인가"를 로그로 확인하자.

Zipf 분포, TTL=20초일 때 전체 원본 요청은 초당 몇 개인가? (차트에서 읽기, 소수 둘째 자리)

4. TTL 정하는 순서

  1. 필드별로 허용 가능한 stale 최대 나이를 정한다 → TTL 상한.
  2. 키별 요청률 분포를 보고 1/(T+1/λ) 합으로 원본 부하를 추정한다.
  3. 원본이 감당할 수 있는 부하 이하가 되는 가장 짧은 TTL을 고른다. 상한을 넘어야 한다면 TTL이 아니라 무효화·사전 갱신을 검토한다.
